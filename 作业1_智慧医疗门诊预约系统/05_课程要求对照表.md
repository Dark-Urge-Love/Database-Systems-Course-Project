## 二、六项基本操作

对应页面：**药房业务 `/ops`** —— 界面按真实业务组织：用户看到的是药品、供应商档案这类业务对象，
直接操作业务单据，六项基本操作各自发生在对应业务场景里；表名与字段名由系统内部处理，不出现在界面上。

| # | 课程要求 | 业务场景（用户操作） | 实际执行的 SQL | 后端接口 |
|---|---|---|---|---|
| 1 | **创建数据表** | 需要登记一类新资料（如供应商档案）→「业务档案」→ 新建档案：填档案名称 + 要记录的信息（供应商名称、联系人、结算金额…） | `CREATE TABLE archive_xxx (id …, f1 …, f2 …) COMMENT='供应商档案'`（档案名/字段名写入表与列注释） | `POST /api/archives` |
| 2 | **插入数据** | 库房到货 →「新药入库」；或登记一家新供应商 →「录入记录」 | `INSERT INTO drug (...) VALUES (%s...)` / `INSERT INTO archive_xxx (f1, f2…) VALUES (%s…)` | `POST /api/pharmacy/drugs`、`POST /api/archives/<档案>/records` |
| 3 | **修改数据** | 药品调价、库存盘点、品种停用 → 药品目录「编辑」 | `UPDATE drug SET price=%s, stock=%s … WHERE drug_id=%s` | `POST /api/pharmacy/drugs/<id>` |
| 4 | **删除数据** | 录入错误的品种 →「删除」；已开过处方的药品会被业务规则拦下（提示改为停用） | `DELETE FROM drug WHERE drug_id=%s` | `POST /api/pharmacy/drugs/<id>/remove` |
| 5 | **删除数据表** | 某类档案不再使用 →「业务档案」里删除该档案（二次确认，记录一并清理） | `DROP TABLE archive_xxx` | `POST /api/archives/<档案>/remove` |
| 6 | **跨数据表操作** | 「运营报表」：医生开药金额排行、患者就诊流水 | 5 表 / 7 表 JOIN（见下） | `POST /api/report` |

### 业务上怎么理解"建表 / 删表"

系统里的「业务档案」相当于药房自定义的资料台账（供应商档案、设备台账、体检记录…）：
新建一类档案 = 建一张表，删除档案 = 删表；档案的字段名称、必填与否由业务人员自己定，
系统自动生成物理表名与列名（`archive_xxx` / `f1..fn`），业务人员无需理解数据库结构。

### 业务规则（让操作像真实系统）

- 同名同规格的药品再次入库 → 提示"目录中已有该品种，请直接调整库存或价格"
- 单价、库存不允许负数；库存必须填整数
- 已产生处方记录的药品不允许删除 → 只能"停用"（对外键约束的业务化包装）
- 删除档案前提示"其中 N 条记录将一并删除"；核心业务档案不可删除

### JOIN 报表

- **5 表**：医生开药金额排行（`prescription_item → prescription → visit → doctor → department`）
- **7 表**：患者完整就诊流水（`appointment → patient → schedule → doctor → department → visit → prescription_item → drug`）

### 安全设计（报告可提）

档案/字段的物理名由系统生成并校验，值全部 `%s` 参数化传入；常见 MySQL 错误码翻译成业务语言
（如 1451 → "该记录正被其他业务引用，不能删除"）。

### 演示建议顺序（约 2 分钟）

1. 「药品目录」→ 新药入库（填名称、规格、厂家、单价、库存）
2. 同一品种再入库一次 → 看业务拦截提示
3. 点「编辑」调价、改库存 → 保存后列表立即变化
4. 录入一个错误品种再「删除」；点一条已开过处方的药 → 看"不能删除，请改为停用"
5. 「业务档案」→ 新建"供应商档案"（现场填 4 个字段）→ 录入一条供应商记录
6. 删除该档案 → 二次确认；「运营报表」生成两张报表

## 三、三项额外功能

| # | 课程要求 | 实现 | 页面 |
|---|---|---|---|
| 1 | **事务支持** | 挂号：`SELECT ... FOR UPDATE` 锁排班行 + `INSERT appointment` + `UPDATE schedule` 三语句同一事务；任一失败整体 `ROLLBACK`；`CHECK (remain_slots >= 0)` 兜底 | `/register` |
| 2 | **索引支持** | `sql/index.sql` 建 7 个索引（幂等存储过程）；`/perf` 对同一查询对比"走索引"与 `IGNORE INDEX` 全表扫描的 `EXPLAIN` 计划与实测耗时 | `/perf` |
| 3 | **多用户并发访问 + 访问性能记录** | ① `/register` 页「并发抢号」：Barrier 对齐 + 10 线程同时挂号，页面输出成功/失败数、号源变化、总耗时；② `tools/concurrency_test.py` 压测 read/write/mixed 三场景，输出 TPS、P50/P95/P99 到 CSV | `/register`、`tools/` |

### 并发不超卖的原理（可写在报告里）

1. `SELECT ... FOR UPDATE` 对同一 `schedule_id` 行加排他锁，后到的事务阻塞等待；
2. 锁内重新校验 `remain_slots > 0`，把"检查—扣减"放进同一个原子区间；
3. 提交后 `remain_slots` 才释放，因此成功预约数恒等于号源减少数，不可能为负。

## 五、答辩演示脚本（约 3 分钟）

1. **首页 `/`**：指出课程要求 → 功能的对照表，同时看到 10 表 22 万行、服务器主机名与 Linux 数据目录（证明数据在服务器上）
2. **`/ops` 药房业务**：新药入库 → 调价 → 删除/停用 → 新建业务档案并录入记录 → 删除档案
3. **`/ops` 报表区**：生成 5 表与 7 表 JOIN 报表，说明跨表操作
4. **`/register`**：提交一次挂号，看号源 N → N−1 与事务 SQL
5. **`/register` 并发区**：10 线程抢号，看"成功数 = 号源减少数"，无超卖
6. **`/perf`**：对比 `type: ALL` 与 `ref`、扫描行数几万 → 个位数、耗时对比

## 六、与"被删除功能"的说明

为保证聚焦课程要求，以下内容已移除（原设计中的扩展，非课程要求）：

- 医生接诊 / 开处方页面（`/clinic`）及其事务、药品查询、药品库存扣减、缴费流水写入
- 首页的预约状态分布、科室排行、药品消耗排行（join 已由 `/ops` 报表覆盖）
- 索引的"真删 / 重建"对照功能（改为 `IGNORE INDEX` 绕过索引，且只忽略真实存在的索引，不修改库结构）
- 预置剧本按钮（最初版本），全部改为用户亲自操作的表单

数据库表结构与 22 万条数据不受影响——处方、缴费等数据仍由 `data_gen.py` 生成并用于 join 报表。
