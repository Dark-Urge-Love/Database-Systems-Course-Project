## 二、六项基本操作

对应页面：**进销存业务 `/ops`** —— 界面按真实业务组织：用户看到的是药品、供应商、采购单、库存这类业务对象，
六项基本操作各自发生在对应业务场景里；表名与字段名由系统内部处理，基本不出现在界面上。

| # | 课程要求 | 业务场景（用户操作） | 实际执行的 SQL | 后端接口 |
|---|---|---|---|---|
| 1 | **创建数据表** | 需要登记一类新资料（如药品召回、冷链温控）→「业务表单」→ 选模板 → 建表单 | `CREATE TABLE bizform_xxx (id …, drug_id INT, f1 …, f2 …) COMMENT='药品召回登记'` + 外键 `fk_bizform_xxx_drug` | `POST /api/forms` |
| 2 | **插入数据** | 库房到货 →「采购入库」；或新增药品 →「药品目录」；或登记一条召回记录 | `INSERT INTO purchase_order/purchase_item/stock_batch/stock/stock_movement …`（**6 表同一事务**）；`INSERT INTO drug …`；`INSERT INTO bizform_xxx …` | `POST /api/purchases`、`POST /api/drugs`、`POST /api/forms/<表单>/records` |
| 3 | **修改数据** | 药品调价、改规格、停用 →「药品目录 · 编辑」 | `UPDATE drug SET retail_price=%s, spec=%s, status=%s … WHERE drug_id=%s` | `POST /api/drugs/<id>` |
| 4 | **删除数据** | 录错的品种 →「删除」；已被采购/销售引用的会被外键拦下（提示改为停用） | `DELETE FROM drug WHERE drug_id=%s` | `POST /api/drugs/<id>/remove` |
| 5 | **删除数据表** | 某类表单不再使用 →「业务表单」→ 删除（二次确认，记录一并清理） | `DROP TABLE bizform_xxx` | `POST /api/forms/<表单>/remove` |
| 6 | **跨数据表操作** | 「运营报表」：供应商供货排行、药品销售排行、效期预警批次溯源、单品流向追溯 | 5 表 / 5 表 / 6 表 / **7 表** JOIN | `POST /api/report` |

### 业务上怎么理解"建表 / 删表"

系统里的「业务表单」相当于质量管理部门的临时台账（召回登记、盘点差异、调价留痕、冷链温控）：
新建一类表单 = 建一张表，删除表单 = 删表；表单的字段名称、必填与否由业务人员自己定，
系统自动生成物理表名（`bizform_xxx`）与列名（`f1..fn`），并自动挂上 `drug_id` 外键关联药品主数据。

### 业务规则（让操作像真实系统）

- 同名同规格的药品再次建档 → 提示"目录中已有该品种（名称+规格唯一），请直接调整价格或库存"
- 采购价 / 零售价不允许负数；数量必须为正整数；有效期必须晚于生产日期
- 已被采购明细或销售明细引用的药品不允许删除 → 只能"停用"（外键 RESTRICT 的业务化包装，错误码 1451）
- 库存不能为负 → 出库前在行锁内校验（业务层拦截）+ `CHECK (quantity >= 0)`（数据库层兜底，错误码 3819）
- 销售出库自动跳过已过期批次，并按近效期先出

### 四张 JOIN 报表（跨表操作）

| 报表 | 表数 | 链路 |
|---|---:|---|
| 供应商供货排行 | 5 | `purchase_item → purchase_order → supplier → warehouse → employee` |
| 药品销售排行 | 5 | `sale_item → sale_order → drug → drug_category → warehouse` |
| 效期预警批次溯源 | 6 | `stock_batch → drug → warehouse → purchase_item → purchase_order → supplier` |
| 单品流向追溯 | 7 | `stock_movement → drug → warehouse → employee` + `LEFT JOIN sale_order / purchase_order / supplier`（按单号关联，未关联也能出） |

### 安全设计（报告可提）

业务表单的表名/列名由系统生成并做标识符白名单校验（只允许字母数字下划线），所有值一律 `%s` 参数化传入；
常见 MySQL 错误码翻译成业务语言：`1451` → "该记录正被其他业务引用，不能删除"，
`3819` → "库存不能为负数"，`1062` → "已存在相同记录"。

## 三、三项额外功能

| # | 课程要求 | 实现 | 页面 |
|---|---|---|---|
| 1 | **事务支持** | ① **采购入库**：单据头 → 明细 → 批次 → 结存（`FOR UPDATE`）→ 流水，**6 张表同一事务**，任一步失败整体 `ROLLBACK`；② **销售出库**：`SELECT … FROM stock … FOR UPDATE` 锁结存行 → 校验库存 → 近效期先出扣批次 → 写单据 → 扣结存 → 写流水，同一事务 | `/ops`（采购入库 / 销售出库） |
| 2 | **索引支持** | `sql/index.sql` 建 24 个普通索引（幂等存储过程 `add_index_if_missing`，可重复执行）；「运营报表 → 单药品出入库全链路」的**索引体检**：对同一条 7 表业务 SQL 对比"走索引"与 `IGNORE INDEX` 全表扫描的 `EXPLAIN` 计划与实测耗时 | `/ops`（运营报表页签） |
| 3 | **多用户并发访问 + 访问性能记录** | `/ops` 页「并发出库」：`threading.Barrier` 对齐 + N 个终端（线程）同时出库同一品种，每个终端在事务内先锁结存行再扣减；页面输出成功/失败数、库存变化、总耗时、平均/最快/最慢响应、吞吐量，并把**每一次访问的耗时**逐条写入 `access_log`（JOIN 药品名可查） | `/ops`（并发出库页签） |

### 并发不超卖的原理（可写在报告里）

1. `SELECT … FROM stock WHERE drug_id=? AND warehouse_id=? FOR UPDATE` 对结存行加排他锁，后到的事务阻塞等待；
2. 锁内重新校验 `quantity >= 本次出库量`，把"检查—扣减"放进同一个原子区间；
3. 提交后行锁才释放，因此"成功次数 × 每次数量"恒等于"库存减少量"，不可能为负；
4. `CHECK (quantity >= 0)` 是数据库层的最后一道防线（即使应用逻辑写错也拦得住）。

## 七、设计上做过的取舍（答辩可能被问到）

| 问题 | 取舍与理由 |
|---|---|
| 为什么库存单独一张表，不放在药品表里？ | 多仓库场景下"一药多仓"是多值属性，放 `drug` 会违反 1NF；独立 `stock(drug_id, warehouse_id)` 并以唯一索引保证"一药一仓一行" |
| 单据头金额 `total_amount` 不是可以从明细算出来吗？ | 可算，但业务上需要"单据头的稳定总额"，属受控冗余：由同一事务写入，并由 6 项自洽校验兜底 |
| 为什么批次价格、销售单价要单独存？ | 它们是**时态快照**（该批成本 / 该次成交价），药品调价后历史单据不能变，与 `drug.retail_price`（当前价）语义不同 |
| 为什么 `access_log` 不设外键？ | 它是性能采样数据，不应因药品主数据维护而阻塞或级联；弱关联 + 普通索引是该场景的合理选择（报告中作为"约束强度 vs 运维灵活度"的讨论点） |
| 索引对比为什么用 `IGNORE INDEX` 而不是真删索引？ | 真删会影响其他演示且需要重建；`IGNORE INDEX` 在同一时刻、同一数据量下对比，更公平且不改库结构 |
| 并发出库为什么先锁 `stock` 再锁 `stock_batch`？ | 结存行是"总闸门"，先锁它把"检查库存 → 扣批次 → 扣结存"整段串行化，避免超卖；再按批次加锁防止两个事务扣同一批 |
