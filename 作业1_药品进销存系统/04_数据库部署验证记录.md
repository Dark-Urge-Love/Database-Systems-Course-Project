## 三、账实自洽检查（实测，全部为 0 行）

| 检查项 | 含义 | 异常行数 |
|---|---|---:|
| 库存结存 ≠ 批次结存之和 | `stock.quantity` 必须等于该药该仓所有批次结存之和 | **0** |
| 流水 `after_qty ≠ before_qty + change_qty` | 账面必须连续，不能跳变 | **0** |
| 采购明细金额 ≠ 数量 × 单价 | `purchase_item.amount` 正确性 | **0** |
| 销售明细金额 ≠ 数量 × 单价 | `sale_item.amount` 正确性 | **0** |
| 库存出现负数 | `stock.quantity >= 0` | **0** |
| 批次结存出现负数 | `stock_batch.quantity >= 0` | **0** |

> 这一组检查证明：数据不是"随机灌数"，而是按业务时间轴推演出来的**账实一致的账套**。

> 踩坑记录（报告可写）：① 早期版本给"待入库"的采购单也生成了批次，导致 1,004 行账实不符；
> ② "盘点调整"只改库存未同步批次，残留 632 行差异。修正后归零。

### 5.3 各仓库库存分布（3 表 JOIN + 聚合）

`warehouse ← stock`，统计每仓的药品品种数、库存总量、低于安全库存的行数。

### 5.4 近效期批次溯源（6 表 JOIN）

`stock_batch → drug → warehouse → purchase_item → purchase_order → supplier`，
筛选 `quantity > 0 AND expiry_date < CURDATE()+180 天`（页面报表口径），输出药品、规格、仓库、批号、结存、
有效期至、剩余天数、采购单价、来源采购单与供应商。

> 自检脚本 `selfcheck_req.py` 用的是更严的 **90 天**口径，实测该口径下仍有结存的近效期批次 **962 个**。

### 5.5 单品流向追溯（7 表 JOIN）

`stock_movement → drug → warehouse → employee` + `LEFT JOIN sale_order / purchase_order / supplier`：
按 `ref_no` 与单号关联，出库行显示客户名称、入库行显示供应商名称，一张表看完某个药品的完整进出账。

### 5.6 库存与效期总览（实测）

| 药品 × 仓库 结存行数 | 6,360 |

## 十二、注意事项

1. **`access_log` 会持续增长**：每次并发出库演示 +N 条（N = 客户端数）。若数据量统计希望保持"干净"，
   可在演示前 `TRUNCATE access_log`；它不计入 12 张业务表的 153,072 条。
2. **压测会临时改库存**：脚本结束后自动恢复原值并删除 `ref_no='BENCH'` 的流水；若中途被强制中断，
   手工执行 `DELETE FROM stock_movement WHERE ref_no='BENCH'` 并按 `concurrency_summary_*.csv` 里的原库存复原。
3. **`data_gen.py` 会先清空再重写**：它是"重建账套"脚本，不要在有真实数据时执行。
4. **账号仅供教学**：`druguser` / `Drug@123456` 是本地虚拟机口令，不要复用到任何真实环境。
